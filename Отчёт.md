# Отчёт: Link Tracker

## 1. Доменная область

**Link Tracker** — бот, который отслеживает изменения на веб-страницах и оперативно информирует пользователя о них. Пользователь добавляет ссылки на репозитории GitHub и вопросы StackOverflow, а сервис периодически проверяет их и показывает уведомления, когда на ссылке появляется что-то новое:

- GitHub: новый issue или pull request;
- StackOverflow: новый ответ на вопрос.

Ссылки можно размечать **тегами** (для группировки) и **фильтрами**. Владельцем ссылок является **чат** — числовой идентификатор пользователя (рабочего пространства).

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Язык  | Go 1.25 |
| Бэкенд | HTTP/REST (HTTP/1.1), JSON, маршрутизация стандартным `http.ServeMux` |
| Планировщик | `gocron/v2` (периодическая проверка ссылок, пул воркеров, батчи) |
| СУБД | PostgreSQL 16 |
| Доступ к БД | `database/sql` + драйвер `pgx/v5` (stdlib), `squirrel` (построение части запросов), `lib/pq` (чтение массивов) |
| Миграции | `golang-migrate` (SQL-файлы вшиты в бинарник через `embed`) |
| Конфигурация | `caarlos0/env` (переменные окружения) |
| Фронтенд | Одна страница на HTML + CSS + JavaScript  |
| Упаковка и запуск | Docker (multi-stage, `distroless`), Docker Compose |



## 3. Основные сущности

| Сущность | Таблица | Описание |
|---|---|---|
| **Chat** | `chats` | Пользователь/рабочее пространство. `id` — числовой идентификатор, задаётся при создании |
| **Link** | `links` | Отслеживаемый URL. Уникален глобально: одну ссылку могут отслеживать несколько чатов, но проверяется она один раз. Хранит `last_seen_at` — время последнего известного обновления |
| **Subscription** | `chat_links` | Связь «чат отслеживает ссылку» (многие ко многим), составной первичный ключ `(chat_id, link_id)` |
| **Tag** | `link_tags` | Тег подписки. Принадлежит паре «чат + ссылка» |
| **Filter** | `link_filters` | Фильтр подписки, устроен как тег |
| **Update** | `updates` | Уведомление об изменении на ссылке, адресованное конкретному чату |

Связи: удаление чата каскадно удаляет его подписки, теги, фильтры и уведомления (`ON DELETE CASCADE`).

### CRUD-операции над сущностями

| Сущность | Create | Read | Update | Delete |
|---|---|---|---|---|
| Chat | `POST /tg-chat/{id}` | `GET /tg-chat?limit=&offset=` | не применима: у чата нет изменяемых полей | `DELETE /tg-chat/{id}` |
| Link (+ теги, фильтры) | `POST /links` | `GET /links?tgChatId=&limit=&offset=` | `PUT /links/{id}` (полная замена тегов и фильтров) | `DELETE /links` (в теле: ссылка и чат) |
| Update | создаётся планировщиком | `GET /updates?tgChatId=&afterId=&limit=` | не применима: уведомление неизменяемо | каскадно при удалении чата |


## 4. Соответствие методологии «12 факторов»

### I. Codebase — кодовая база

Одна кодовая база под управлением Git, из неё собирается один развёртываемый артефакт — образ `scrapper`. Dockerfile собирает только `./cmd/scrapper`.


### II. Dependencies — зависимости

Все зависимости явно объявлены в `go.mod` с точными версиями и зафиксированы контрольными суммами в `go.sum`. Сборка в Docker начинается с `go mod download` на чистом образе, то есть не опирается ни на что, установленное на машине разработчика. Бинарник собирается статически (`CGO_ENABLED=0`), поэтому от окружения запуска не требуется системных библиотек.

### III. Config — конфигурация

Вся конфигурация, зависящая от окружения, читается из **переменных окружения** (`internal/config`): строка подключения к БД (`DATABASE_DSN`, обязательная), адрес прослушивания, интервал и параметры планировщика. Значения проверяются при старте: приложение завершается с понятной ошибкой, если обязательной переменной нет или значение недопустимо.

Секреты не хранятся ни в коде, ни в образе: `.env` исключён из Git (`.gitignore`) и из контекста сборки (`.dockerignore`), в репозитории лежит только шаблон `.env`. В `docker-compose.yml` значения подставляются из окружения (`${VAR}`), пароль БД обязателен (`${POSTGRES_PASSWORD:?...}`). Значения по умолчанию заданы только для нерегиональных параметров.

### IV. Backing services — сторонние сервисы

PostgreSQL, GitHub API и StackOverflow API рассматриваются как подключаемые ресурсы, адрес и учётные данные которых задаются конфигурацией. Базу данных можно заменить (локальный контейнер, управляемый сервис в облаке) сменой `DATABASE_DSN` без изменения кода. Внутри Docker-сети к базе обращаются по имени сервиса (`postgres:5432`), снаружи — по пробрасываемому порту.

### V. Build, release, run — сборка, релиз, запуск

Этапы разделены:

- **Сборка** (`docker compose build` / `docker build`): multi-stage `Dockerfile` — стадия `golang:1.25-alpine` компилирует бинарник (фронтенд и миграции вшиваются в него), стадия `distroless` содержит только бинарник.
- **Релиз**: неизменяемый образ + конфигурация окружения. Один и тот же образ может запускаться с разной конфигурацией без пересборки.
- **Запуск** (`docker compose up`): процесс стартует с конфигурацией из окружения, изменять код в рантайме невозможно.

### VI. Processes — процессы

Приложение не хранит состояние в памяти процесса и не требует «липких» сессий. Всё, что нужно помнить, лежит в PostgreSQL:

- чаты, ссылки, подписки, теги и фильтры;
- уведомления (таблица `updates`);
- **состояние планировщика** — время последнего известного обновления каждой ссылки (`links.last_seen_at`);
- состояние интерфейса («последнее показанное уведомление») хранится в браузере и при перезагрузке страницы запрашивается заново.

Процесс можно в любой момент остановить и запустить заново, ничего не потеряв.

### VII. Port binding — привязка портов

Сервис самодостаточен: сам открывает HTTP-порт (`SCRAPPER_LISTEN_ADDR`, по умолчанию `:8081`) и обслуживает и API, и статику. Для работы не требуется внешний веб-сервер или контейнер приложений. В Docker порт проброшен на хост через `SCRAPPER_PORT`.

### VIII. Concurrency — параллелизм

Масштабирование возможно двумя способами:

- **Внутри процесса** — пул воркеров (`SCRAPPER_WORKER_COUNT`) параллельно проверяет ссылки, размер батча настраивается (`SCRAPPER_BATCH_SIZE`). HTTP-запросы обслуживаются отдельными горутинами.
- **Горизонтально** — можно запустить несколько экземпляров `scrapper` над одной базой. Чтобы экземпляры не отправляли пользователю одно и то же уведомление дважды, фиксация нового состояния ссылки выполняется атомарным `UPDATE ... WHERE last_seen_at IS NOT DISTINCT FROM <ожидаемое значение>` (compare-and-swap): событие обрабатывает ровно тот экземпляр, чей `UPDATE` затронул строку.


### IX. Disposability — утилизируемость

- **Быстрый старт**: загрузка конфигурации, подключение к БД, применение миграций и запуск сервера занимают доли секунды, прогрева нет.
- **Корректная остановка**: на `SIGTERM`/`SIGINT` сервис перестаёт принимать новые соединения, дожидается обработки активных запросов (таймаут 5 с), затем останавливает планировщик (дожидаясь текущей проверки) и только после этого закрывает соединение с БД. В Compose задан `stop_grace_period: 20s`, чтобы Docker не прервал остановку преждевременно.
- **Устойчивость к внезапному завершению**: операции записи в БД выполняются транзакциями, поэтому аварийная остановка (`SIGKILL`, сбой) не оставляет частично записанных данных; ссылка, не проверенная из-за сбоя, будет проверена в следующем цикле. Контейнер перезапускается автоматически (`restart: unless-stopped`).

### X. Dev/prod parity — идентичность окружений

Разработка и запуск используют одно и то же: тот же образ приложения, ту же СУБД (PostgreSQL 16 в контейнере) и те же миграции, которые применяются автоматически при старте. Окружение поднимается одной командой `docker compose up`, различается только конфигурация (пароли, порты, токены). Для локальной разработки можно запустить только базу в Docker, а приложение через `go run`: код и схема БД остаются теми же.

### XI. Logs — журналы

Приложение не управляет файлами журналов и не занимается их ротацией: все события пишутся потоком в `stdout` в формате JSON (`log/slog`) с уровнем, временем и структурированными полями (идентификатор чата, URL, причина ошибки). Сбор и хранение логов — задача окружения (`docker compose logs`, системы сбора логов).

### XII. Admin processes — задачи администрирования

Единственная задача администрирования — миграции схемы БД. Они вшиты в бинарник и применяются при старте с помощью `golang-migrate`; библиотека берёт advisory-блокировку в PostgreSQL, поэтому одновременный запуск нескольких экземпляров не приводит к двойному применению миграций. Миграции выполняются тем же кодом и в том же окружении, что и приложение, и версионируются вместе с ним (`migrations/*.up.sql` / `*.down.sql`, откат доступен). Других разовых административных задач (наполнение данными, отчёты) в приложении нет.

## 6. Запуск

```bash
docker compose up --build -d
```

Веб-интерфейс: <http://localhost:8081>. Логи: `docker compose logs -f scrapper`. Остановка: `docker compose down` (с флагом `-v` — вместе с данными БД).
